§ Context
01Context

Arrivia's redesigned Support Portal had been sitting in the queue for months. The design was approved. Engineering had scoped it at 2+ months of work — and that estimate didn't include search functionality. With a small dev team in high demand, the project was slated to wait.

This is a familiar pattern at most companies. Design moves faster than engineering can absorb it, work piles up in the backlog, and the gap between "designed" and "shipped" widens. Tools like Figma Make and Stitch help with the design-to-prototype handoff, but they stop where production begins.

I wanted to see if I could close that gap — not by replacing engineering, but by getting the work 90% of the way there so the team could focus on what only they could do: production hardening, integration, and launch.

§ Approach
02Approach

The thesis was simple: if Claude Code could read Figma directly and operate a browser, a designer with no formal engineering background could ship production code by directing the work rather than writing it. The skill being tested wasn't coding — it was system design, judgment, and QA.

Treat it like real engineering, not a prototype demo.

I set up an isolated EPiServer instance so nothing touched production, and I built a reusable Claude Skill — a command like /optimizely-dev that captures the full setup, troubleshooting steps, and project templates. The skill meant the next portal, the next environment, the next teammate could start from one command instead of re-discovering everything. This was the part that mattered most strategically: not the portal, but the repeatable system.

Connect Claude to both ends of the pipeline.

Figma MCP gave Claude direct read access to the design files. Chrome MCP let it operate the browser, take screenshots, and compare its output against the Figma source in real time. The loop was: read design → write code → render → screenshot → compare → fix. Minutes per iteration, not days.

Plan first, then build.

Before any code was written, Claude produced an implementation plan I reviewed and approved. Models, views, CSS, JS, search behavior, error states — sequenced and explicit. Most AI-build failures I've seen come from skipping this step and asking the model to figure it out as it goes. Planning is where design judgment compounds.

Stay in the QA seat.

My job during the build wasn't to write code — it was to direct, review, and reject. When the sidebar icons came back inconsistent in stroke weight, I caught it. When the empty search state was technically functional but visually weak, I rewrote the spec. The model is fast and tireless; the design judgment has to come from somewhere, and so does the engineering judgment that turns "working" into "production."

§ The Work
03The Work

The portal shipped with everything in the original spec plus search functionality the original estimate had cut: sidebar navigation, FAQ accordions, live search with results and error states, responsive breakpoints, and white-label CSS theming so the same portal could re-skin per partner.

One representative iteration loop tells the story of how the system worked end-to-end. The first sidebar pass came back using Font Awesome icons that didn't match Figma. I flagged the mismatch. Claude pulled the eleven custom SVGs from Figma directly, validated them, fixed the preserveAspectRatio attribute that was stretching them, and updated the CSS — all in a single pass.

§ Impact
04Impact

I handed the build off to engineering with a complete implementation plan — which files to copy, what to configure, what to watch out for. The team is now bringing it to production.

The headline number is ~85% time saved against the original estimate. The more durable outcome is the Claude Skill built during the project, which is now reusable infrastructure for future EPiServer work — meaning the next project doesn't start from scratch.

I presented this work at Arrivia's internal AI Hackathon to the broader product and engineering org. The framing — bringing dev superpowers to everyone — became a recurring conversation about what the team's delivery model could look like if every designer worked this way.

§ Reflection
05Reflection

The instinct most designers have when they see AI tools is to use them for inspiration — moodboards, first drafts, brainstorming. That's the smallest version of the bet.

The bigger version is: redesign your delivery model around them. Build skills, set up environments, treat your AI as a collaborator with clear specs and a tight feedback loop. The 85% number isn't about Claude being magic — it's about removing the handoff between design and production, which is where most product work goes to die.

What I'd do differently next time: bring engineering in from day one, not at handoff. Their context on the existing codebase, deployment patterns, and edge cases would have made the build sharper. The technical work and the collaboration work are the same work.
